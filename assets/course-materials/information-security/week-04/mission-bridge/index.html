This happened for real

When an untested release goes global

Two widely reported incidents show why a release gate is not paperwork — it is the last check before a bug becomes a headline.

CrowdStrike outage (2024)

A faulty content update to CrowdStrike's Falcon sensor was pushed straight to production and, as widely reported, crashed millions of Windows machines worldwide — grounding flights, disrupting hospitals, and knocking banks and broadcasters offline for days.

Lesson: the update reportedly skipped a staged rollout and adequate pre-release validation. A release gate that requires canary deployment and rollback testing exists precisely to catch this before it reaches every machine at once.

Knight Capital (2012)

Knight Capital deployed new trading code to only some of its production servers, leaving old, repurposed test code active on the rest. In the roughly 45 minutes before the mismatch was caught, it reportedly cost the firm about $440 million and led to its collapse.

Lesson: inconsistent deployment across servers is itself a release-gate failure — a gate should verify the deployed state matches the intended state everywhere, not just that the code compiled.

Tie-in: the same triage habit from Checkpoint 1 is what stood between these companies and the outage. Treat "no rollback plan" and "partial or unverified deployment" as Block-level findings, the same way you would an authentication bypass.
