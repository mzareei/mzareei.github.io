Definition

What is authentication?

“The process of establishing confidence in user identities that are presented electronically to an information system.”
— NIST SP 800-63 (Digital Identity Guidelines)
Key

The word is confidence. Authentication isn't absolute certainty — it's raising confidence enough for the risk at hand.

Current standard

The current reference is NIST SP 800-63-4 (Revision 4, finalized 2024–2025), which superseded the 2016 SP 800-63-3. We'll follow its modern guidance throughout this lecture.

Don't confuse these

Authentication vs. authorization

🪪

Authentication — who you are

Verifies your identity. Are you really Mahdi?

🔑

Authorization — what you can do

Decides your permissions once identified. May Mahdi enter this room?

Analogy

At the airport: your passport authenticates you (who you are); your boarding pass authorizes you (which flight and seat). One then the other.

Two goals in tension

Authentication goals: two errors to avoid

Availability

The legitimate user must be able to authenticate. Avoid false negatives (rejecting the real person).

Authenticity

Someone who is not the user must not authenticate. Avoid false positives (accepting an impostor).

Discuss

Which is worse: a bank vault that occasionally lets an impostor in, or one that occasionally locks out the rightful owner? And for unlocking your phone? The answer depends on context.

01

How do we prove who you are?

The four authentication factors.

Four means (alone or combined)

The four authentication factors

🧠

Something you know

Password, PIN, answers to questions. Risk: can be guessed or stolen.

🔐

Something you have

Keycard, token, physical key, phone code. Risk: can be lost or forged.

🧬

Something you are (static biometrics)

Fingerprint, iris, face. Risk: you can't change it if it leaks.

✍️

Something you do (dynamic biometrics)

Voice, handwriting, typing rhythm. Risk: varies with the person's state.

Everyday example: your ATM card (have) + your PIN (know) = two factors.

Sliding the threshold right blocks more impostors but rejects more real users. And remember: if your fingerprint is stolen, you can't "change" it like a password. Should biometrics replace passwords?

Presentation attacks

Those rates assume an honest attacker. But biometrics can also be spoofed: gelatin "gummy" fingerprints, a printed photo or a deepfake for face unlock. That's why good systems add liveness detection. Debate: is liveness enough, or will a motivated attacker always find the gap?

02

Passwords

The most-used line of defense — and the most mis-implemented.

The basics

Password-based authentication

  • The user provides a name/login and a password; the system compares it with the one stored for that login.
  • The user ID determines whether they're authorized to access the system.
  • The ID determines the user's privileges (e.g., normal user vs. "superuser").
  • It's used in discretionary access control (DAC).
Everyday example

When you log into the university's grades portal, your student ID determines which records you can see — your own, not another student's — even though the password already confirmed who you are.

How to check the password?

Method 1: store the list of passwords (don't!)

Store one password per user in the system file, readable only by root/admin.

What could go wrong?

What if the permissions are set wrong? Why should the admin know your password at all? If there's a breach, every password is exposed to the attacker.

This is why this option is essentially forbidden in any serious system.

A better idea

Method 2: don't store the password — store its hash

We store something derived from the password using a one-way hash function; at login we hash what's typed and compare the hashes.

Idea

The admin never sees your password; only hashes are compared. Even if the file is stolen, they don't get the passwords… directly.

Hash functions

What makes a hash function special?

One-way

Easy to compute forward; infeasible to reverse.

Deterministic

Same input → always the same hash.

Fixed length

Any input → same-size output.

Analogy

Like a blender: turning fruit into a smoothie is trivial; reconstructing the exact fruit from the smoothie is not. Or like a fingerprint of the data.

Live in the terminal

Demo: determinism, avalanche, and salt

echo -n "myfirstpet" | sha256sum e3b1c4...8a2f9d - echo -n "myfirstpet" | sha256sum # same input again e3b1c4...8a2f9d - # identical → deterministic echo -n "myfirstpeu" | sha256sum # one letter changed 7f0a92...c14b06 - # totally different → avalanche echo -n "x7Qz!myfirstpet" | sha256sum # same password + a salt a14d77...20e9c3 - # different again → salt changes output
Three lessons

1) Same input always gives the same hash. 2) Changing one character changes the whole digest (avalanche effect). 3) Prepending a salt produces a different hash even for the same password.

Digests abbreviated for display; run it yourself to see the full 64-hex values.

Threat model

Assume the attacker already has the hash file

We assume the one-way property — but also that the attacker obtained the file (the shadow file).

Dictionary attack

If we know common passwords, we hash them and look for matches.

Offline attack

With the hashes in hand and plenty of time, the attacker tests endlessly — no lockouts.

Case study

LinkedIn, 2012: why salt and slowness matter

What went wrong

LinkedIn stored ~117 million passwords as unsalted SHA-1. SHA-1 is fast, and without salt, precomputed tables work perfectly.

The outcome

The vast majority of hashes were cracked quickly once the dump spread in 2016. (Compare: RockYou, 2009, stored 32 million in plaintext.)

The lesson

Per-user salt + a deliberately slow function (bcrypt/Argon2) would have turned an instant catastrophe into an infeasible attack. We'll see exactly that in the next slides.

Brute force

How long until a password falls?

PasswordTime to crack
8 chars, lowercase only≈ 3 weeks

Discuss

Each extra character multiplies the work. That's why a long passphrase ("correct horse battery staple") can beat "P@ss1!". Long-and-memorable, or short-and-complex?

Hive Systems, 2025, assuming a slow, salted hash (bcrypt, cost factor 10) on a 12× RTX 5090 rig. Note: against a fast, unsalted hash like MD5/SHA-1, the same passwords fall in minutes-to-hours — which is exactly why we use slow, salted hashing (see the key-stretching slide).

The measure: entropy

Length beats symbols

A password's strength is measured in bits of entropy ≈ log₂( charset-size length ). Each extra bit doubles the attacker's work.

"P@ss1!" — short and "complex"

6 chars from a large charset ≈ ~39 bits. Hard to remember, easy for a modern cracker.

"correct horse battery staple"

4 random words from a common list ≈ 44+ bits — stronger and easier to remember (the XKCD comic idea).

Takeaway

Adding length raises entropy faster and cheaper than adding odd symbols. A four-word passphrase beats "P@ss1!" on both security and memorability.

The attacker is smart

Attackers don't guess at random

  • Passwords are not really random — people pick memorable things.
  • They try popular passwords first (123456, password, names…).
  • They shrink the search space with social engineering (your pet, your team, your birthday).
Reflect

Look back at the earlier table: "myfirstpet", "myboyfriend"… how many would fall in the first second of a dictionary attack?

Salt

What if two users pick the same password?

Add a random salt before hashing; store it with the hash; to verify, use the same salt with the typed password.

UserPasswordSaltHash( password + salt )
Anaverano20249f3aB1C4…77E2
Betoverano20242db804AF…9C10
The point

Same password, different hashes. Like adding a unique ingredient to each recipe: two identical dishes end up tasting different.

Why salt matters so much

Salt defeats precomputed tables

Rainbow tables

The attacker precomputes hashes of millions of passwords once, then instantly looks up matches in any stolen file.

Salt breaks them

A unique per-user salt forces recomputation for every single user — precomputation no longer helps.

In short

Without salt: cracking a million-account file costs almost the same as cracking one. With salt: it costs a million times more.

Make each guess deliberately slow

Idea

Repeating the hash thousands of times is unnoticeable for one honest login, but multiplies a brute-force attack's cost by thousands. Use deliberately slow functions: bcrypt, scrypt, Argon2, PBKDF2 — not fast MD5/SHA.

The underlying problem

Passwords are a necessary evil

Usability vs. security

More length/complexity → worse usability. Usable passwords are easy to guess.

Phishing

Users don't authenticate who is asking for the password.

Reuse

Stolen once, used many times — and across many sites.

Human memory

We remember few; for years that drove frequent-change policies.

Current NIST guidance

Per NIST SP 800-63B-4, verifiers SHALL NOT force periodic rotation (only on evidence of compromise), SHALL NOT impose composition/complexity rules, should favor length over complexity, screen against known-breached-password blocklists, require a minimum of 8 characters (15 when the password is the sole authenticator), allow up to 64, and allow paste and password managers.

What changed and why

The old advice — "change it every 90 days" and "use special characters" — is no longer best practice: forced rotation led to worse, predictable passwords (summer2024 → summer2025). We keep it only as a historical contrast.

Best practices

What to do (admins & users)

System administrators

• Never store passwords in the clear.
• Store only hashes with a random salt, and limit access.
• Avoid fast general-purpose hash functions.
• Screen against known-breached passwords and reject compromised ones.

Users

• Use a password manager.
• Long, unique passwords per site.
• Turn on a second factor.

An attacker would have to defeat two different kinds of factor at once. Stealing your password is no longer enough.

Why the extra step is worth it

🛡️

Survives a database breach

🙂

Enables smoother sign-ins without sacrificing security.

The practical combo

Password manager + 2-step verification

🗝️

Password manager

Generates and remembers a long, unique password per site — you only remember one master key.

📲

Second step

An authenticator app (time-based codes) or a security key adds the "have" factor.

Debate

A manager puts everything in one place: isn't that a "single point of failure"? What still makes it safer than reusing passwords?

Rule of thumb

Any MFA beats none. But if you can choose, climb the ladder: SMS < app < key/passkey.

The weak link

Why is the SMS code weak?

🔄

SIM-swap

The attacker tricks the carrier into moving your number to their SIM and receives your codes.

🎣

Real-time phishing / relay

A fake site asks for the code and relays it to the real site instantly.

📡

Interception

Signaling networks (SS7) and phone malware can read the messages.

Regulatory trend

For these reasons, regulators and major platforms are phasing out SMS OTP as a second factor. Use it only when nothing better is available.

Passwordless, phishing-resistant

Passkeys: FIDO2 / WebAuthn

A passkey is a cryptographic key pair: the private key never leaves your device; the site only stores the public key. There is no shared secret to steal.

Phishing-resistant

The credential is origin-bound (the real domain). A fake site can't elicit a valid signature — the browser refuses.

Nothing to leak

A server breach only exposes public keys, useless for impersonating you.

Connect

Recall the network/MITM slide: passkeys resist replay and phishing precisely because they're origin-bound. Mainstream across Apple, Google, and Microsoft since 2024–2025.

Inside the system

Authentication in the OS

  • The OS (the TCB, trusted computing base) needs to know who requests a protected resource.
  • A process makes the request on behalf of a user, subject, or principal.
  • Authentication answers: on whose behalf does this process run?
Connect

This links back to last week: identity → authentication → authorization → access control.

Everyday example

This is why sudo on Linux/macOS (or the User Account Control prompt on Windows) asks you to re-authenticate before a process can act as administrator: the OS needs to reconfirm on whose behalf that elevated-privilege process is running.

Summary

Authentication, in one slide

  • Authentication is a key requirement for securing access to resources.
  • Four factors — know, have, are, do — with trade-offs to balance.
  • Never store passwords in clear: hash + salt + stretching.
  • The security mindset requires careful threat modeling at every decision.
